# Сервис анализа технического обращения

Сервис принимает техническое обращение, валидирует входной JSON, подбирает релевантные записи из локального справочника, вызывает локальную языковую модель через `llama.cpp server`, проверяет ответ модели и возвращает структурированный результат анализа.

Проект настроен на локальную модель `Qwen3-0.6B-GGUF` в квантизации `Q4_K_M` через endpoint `/v1/chat/completions`. Внутренний prompt, справочный контекст и ожидаемый ответ модели сформулированы на английском, чтобы модель стабильнее возвращала структурированный JSON.

## Технологии

- Python 3.10+
- FastAPI
- Pydantic v2
- httpx
- pytest
- Docker / docker-compose
- llama.cpp server
- Qwen3-0.6B-GGUF Q4_K_M

## Структура проекта

```text
app/
  main.py             # FastAPI-приложение и маршруты
  models.py           # Pydantic-схемы входа, выхода и ответа модели
  service.py          # Основной сценарий обработки обращения
  llm_client.py       # Вызов локальной LLM через llama.cpp и парсинг JSON
  knowledge_base.py   # Внутренний справочник и поиск релевантных записей
  config.py           # Настройки из переменных окружения
  logging_config.py   # Настройка журналирования
tests/
  test_service.py     # Минимальные автотесты
models/
  Qwen3-0.6B-Q4_K_M.gguf # файл модели, загружается при поднятии докера
```

## Локальная модель

Для запуска без Docker создайте папку для модели:

```bash
mkdir -p models
```

Скачайте файл `Qwen3-0.6B-Q4_K_M.gguf` со страницы Hugging Face `lmstudio-community/Qwen3-0.6B-GGUF` и положите его сюда:

```text
models/Qwen3-0.6B-Q4_K_M.gguf
```

Прямая ссылка на файл модели:

```text
https://huggingface.co/lmstudio-community/Qwen3-0.6B-GGUF/resolve/main/Qwen3-0.6B-Q4_K_M.gguf?download=true
```

## Локальный запуск без Docker

Сначала запустите `llama.cpp server`:

```bash
./llama-server \
  -m ./models/Qwen3-0.6B-Q4_K_M.gguf \
  --host 0.0.0.0 \
  --port 8080 \
  --ctx-size 8192 \
  --jinja
```

Проверьте, что сервер модели поднялся:

```bash
curl http://localhost:8080/health
```

Затем запустите FastAPI-сервис:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Проверка сервиса:

```bash
curl http://localhost:8000/health
```

## Запуск через Docker

Docker Compose автоматически скачивает `Qwen3-0.6B-Q4_K_M.gguf` при первом запуске, если файла еще нет:

```bash
cp .env.example .env
docker compose up --build
```

Compose запускает три сервиса:

- `model-downloader` скачивает GGUF-файл в `./models/` и завершается.
- `llama-cpp` запускает сервер модели на порту `8080`.
- `ticket-ai-service` запускает FastAPI-сервис на порту `8000`.

Скачанная модель сохраняется здесь:

```text
models/Qwen3-0.6B-Q4_K_M.gguf
```

Повторные запуски `docker compose up` используют уже скачанный файл.

Внутри Docker Compose приложение обращается к модели по адресу:

```env
LLM_BASE_URL=http://llama-cpp:8080/v1
```

## Пример запроса

```bash
curl -X POST http://localhost:8000/api/v1/analyze \
  -H 'Content-Type: application/json' \
  -d '{
    "ticket_id": "T-1001",
    "source": "monitoring",
    "priority": "high",
    "service": "internet",
    "description": "Packet loss and latency increased on network node sw-01",
    "metrics": {
      "error_rate": 0.25,
      "affected_users": 120,
      "node": "sw-01"
    }
  }'
```

## Переменные окружения

| Переменная            | Назначение                                                                          |
|-----------------------|-------------------------------------------------------------------------------------|
| `LLM_PROVIDER`        | Отображаемое имя провайдера модели, по умолчанию `llama.cpp`.                       |
| `LLM_API_KEY`         | Опциональный ключ доступа. Для обычного локального llama.cpp можно оставить пустым. |
| `LLM_BASE_URL`        | Base URL OpenAI-compatible API. Для локального запуска: `http://127.0.0.1:8080/v1`. |
| `LLM_MODEL`           | Имя модели, которое передается в Chat Completions API.                              |
| `LLM_TIMEOUT_SECONDS` | Таймаут вызова модели.                                                              |
| `LLM_MAX_RETRIES`     | Количество повторных попыток после первого вызова. Минимум `1`.                     |
| `LLM_TEMPERATURE`     | Температура генерации. Для структурированного JSON используется `0.1`.              |
| `LLM_MAX_TOKENS`      | Максимальное число токенов ответа модели.                                           |
| `LOG_LEVEL`           | Уровень логирования.                                                                |

## Ключ доступа к модели

Для локального `llama.cpp server` ключ доступа обычно не нужен, поэтому `LLM_API_KEY` может быть пустым. Если локальный endpoint закрыт reverse-proxy или API-шлюзом, ключ передается через переменную окружения `LLM_API_KEY`.

## Запуск тестов

```bash
pytest -q
```

В тестах языковая модель заменяется fake-клиентом, чтобы автотесты не зависели от локальной модели и сети. В рабочем сценарии используется реальный HTTP-вызов локального `llama.cpp server`.

## Внутренний справочник

Справочник находится в `app/knowledge_base.py` и содержит пять типов технических проблем:

1. PPPoE authentication failures.
2. IPTV or multicast issues.
3. Packet loss or latency increase on a network node.
4. Equipment unavailable.
5. Monitoring alarm events.

Записи справочника содержат `id`, `title`, `problem_type`, ключевые слова, симптомы и рекомендуемые проверки. Справочник сформулирован на английском, потому что этот текст передается в контекст локальной LLM.

## Выбор справочной записи

Функция `find_relevant_records()` собирает текст из `service`, `description`, `metrics.node` и `source`, затем считает совпадения с ключевыми словами записей справочника. Возвращаются до трех наиболее релевантных записей.

Если релевантных записей нет, сервис продолжает обработку: модель получает контекст о том, что справка не найдена, а итоговый результат помечается как `partial_success` и `needs_human_review=true` при успешном ответе модели.

## Проверка ответа языковой модели

Проверка находится в `app/llm_client.py`:

- `parse_llm_response()` проверяет, что ответ является корректным JSON-объектом.
- Перед парсингом удаляются типичные обертки локальных моделей: `<think>...</think>` и markdown code fence.
- `LLMStructuredResult` проверяет обязательные поля, strict-типы, непустой список `recommended_actions`, допустимый `risk_level` и запрещает лишние поля.
- Дополнительно выполняется базовая проверка непротиворечивости: критичный входной приоритет нельзя понизить ниже `high`.
- Ответ модели также проверяется на явное противоречие найденному справочному контексту.

Если ответ модели не проходит проверку, сервис не падает: выполняется повторная попытка, а затем безопасный fallback-ответ при необходимости.

## Определение риска

Риск уточняется в `calculate_risk()` в `app/service.py`. Учитываются:

- входной `priority`;
- `metrics.error_rate`;
- `metrics.affected_users`;
- риск, предложенный языковой моделью;
- отсутствие релевантных записей справочника.

Сервис не понижает риск ниже значимых входных признаков.

## Обработка ошибок

Сервис обрабатывает:

- отсутствие обязательных полей через FastAPI / Pydantic `422`;
- недопустимые значения `priority` и `source`;
- неверный тип `metrics.affected_users`;
- неверный тип или диапазон `metrics.error_rate`;
- недоступность локальной LLM;
- пустой ответ модели;
- невалидный JSON от модели;
- JSON модели не по ожидаемой структуре;
- отсутствие релевантных записей справочника.

При сбое языковой модели сервис выполняет не менее одной повторной попытки. Если корректный ответ получить не удалось, возвращается безопасный структурированный ответ со статусом `failed` и `needs_human_review=true`.

## Журналирование

Логируются:

- факт получения HTTP-запроса;
- `ticket_id`;
- успешная и неуспешная входная валидация;
- результат поиска по справочнику;
- факт вызова языковой модели;
- ошибка вызова модели, если она возникла;
- результат проверки ответа модели;
- итоговый статус обработки;
- время выполнения ключевых этапов.

Логи пишутся в `stdout`. При запуске через Docker Compose их можно посмотреть командой:

```bash
docker compose logs -f ticket-ai-service
```

В журнал нельзя записывать:

- ключи доступа, если они появятся в инфраструктуре вокруг сервиса;
- токены;
- пароли;
- полные персональные данные;
- чувствительные внутренние документы;
- полный prompt к языковой модели, если он содержит чувствительные данные.

## Использование ИИ-инструментов

При подготовке решения использовался ИИ-агент Codex для генерации и доработки структуры проекта, README и тестовых сценариев.

Вручную были доработаны:

- структура модулей;
- правила определения риска;
- внутренний справочник;
- fallback-ответ;
- обработка ошибок;
- Docker Compose с автоматической загрузкой модели;
- prompt для локальной Qwen3-модели;
- проверки ответа LLM;
- тестовые сценарии;
- перевод runtime-части на английский язык для LLM.

После генерации были найдены и исправлены ограничения:

- нестрогая проверка типов входных `metrics`;
- нестрогая проверка типов ответа LLM;
- отсутствие логирования неуспешной входной валидации;
- отсутствие проверки ответа модели на противоречие справочнику;
- риск, что модель всегда вернет `needs_human_review=true` из-за literal-примера в prompt;
- риск, что ввиду использования маленькой локальной модели, ответы будут возвращаться некорректные, в следствии чего были переведены промпты на английский язык;
- устаревшие версии зависимостей, в которых были обнаружены уязвимости, обновлены до актуальных версий.

Самостоятельно приняты решения:

- использовать локальный `llama.cpp server` для локального запуска модели;
- использовать `lmstudio-community/Qwen3-0.6B-GGUF Q4_K_M` как легкую локальную модель для прототипа;
- оставить `LLM_API_KEY` опциональным для совместимости с защищенным локальным endpoint;
- использовать `/no_think`, чтобы снизить риск вывода reasoning перед JSON;
- очищать `<think>...</think>` и markdown code fence перед JSON-парсингом;
- использовать keyword-поиск вместо векторного поиска, потому что сложный RAG в задании не требуется;
- не логировать полный prompt.

## Ограничения текущего решения

- Поиск по справочнику keyword-based, без embeddings.
- Качество анализа зависит от выбранной локальной модели и квантизации.
- Модель 0.6B работает быстрее крупных моделей, но может давать менее качественный анализ.
- Нет авторизации и разграничения доступа.
- Нет хранения истории обращений.
- Нет промышленного мониторинга и distributed tracing.
- Логика риска простая и требует настройки на реальных данных.

## Самопроверка решения

1. Что произойдет, если во входном запросе нет `description`?
Ответ: FastAPI и Pydantic вернут HTTP `422`, а обработчик валидации запишет это в журнал без полного тела запроса.
2. Что произойдет, если `priority` имеет недопустимое значение?
Ответ: Pydantic отклонит запрос с HTTP `422`, потому что допустимы только `low`, `medium`, `high` и `critical`.
3. Что произойдет, если языковая модель вернет обычный текст вместо JSON?
Ответ: `parse_llm_response()` выбросит `LLMError`, сервис выполнит повторную попытку и затем вернет безопасный ответ со статусом `failed`.
4. Что произойдет, если языковая модель недоступна?
Ответ: HTTP-ошибка будет преобразована в `LLMError`, после повторной попытки сервис вернет fallback-ответ с `needs_human_review=true`.
5. Где в коде проверяется структура ответа языковой модели?
Ответ: в `app/llm_client.py`: функция `parse_llm_response()` парсит JSON, а модель `LLMStructuredResult` проверяет поля, типы и допустимые значения.
6. Где определяется уровень риска?
Ответ: в `calculate_risk()` в `app/service.py` на основе входного `priority`, метрик, ответа модели и наличия релевантного справочного контекста.
7. Где выполняется поиск по внутреннему справочнику?
Ответ: в `find_relevant_records()` в `app/knowledge_base.py`.
8. Какие данные нельзя писать в журнал?
Ответ: ключи доступа, токены, пароли, полные персональные данные, чувствительные внутренние документы и полный prompt к модели.
9. Как заменить одну языковую модель на другую?
Ответ: изменить `LLM_MODEL`, при необходимости `LLM_BASE_URL`, и запустить совместимый OpenAI-compatible endpoint, например другой `llama.cpp server`.
10. Что бы вы доработали перед пилотным использованием?
Ответ: авторизацию, аудит, маскирование персональных данных, расширенный справочник, метрики качества и проверку нескольких моделей на реальных обращениях.

## Что доработать перед пилотом

- Добавить авторизацию и аудит доступа.
- Расширить справочник и вынести его в конфиг или БД.
- Добавить Prometheus-метрики.
- Добавить защиту от prompt injection.
- Добавить маскирование персональных данных перед отправкой в модель.
- Добавить оценку качества ответа модели на размеченных кейсах.
- Проверить несколько моделей и квантизаций на реальных обращениях и выбрать баланс качества/скорости.
